## Implementation map and lifecycle

1. `src/BoardShareDialog.tsx:20-58` opens Share, prepares an archive, shows preparing/uploading/confirming states and only shows the link after completion. `src/AppState.tsx:167` serializes archive preparation. `src/boardArchive.ts` exports the fixed board snapshot, including notes, geometry/camera, theme and local/curated images; `src/boardSharing.ts:39-77` checks 32 MiB, hashes it, creates a share, PUTs to R2 and completes it. Upload failure leaves a pending reservation until its 30-minute deadline. A second attempt creates another share.
2. `api/boardShares.ts:51-96` exposes public `POST create`, token-gated `POST complete`, public `GET resolve`, and operations-key-gated `POST cleanup/disable`. There is no public list/read/write/delete by object key. Create/complete require exact configured Origin, which is a browser boundary, not authentication. Vercel-derived `X-Forwarded-For` is HMAC-pseudonymized for rate limits; non-Vercel environments fail closed (`api/boardShares.ts:24-35`). The legacy creator-sign-in helpers remain in `_lib`, but no public creator login or passphrase gate is called. The same signing secret serves as the operations bearer key.
3. `api/_lib/shareService.ts:5-40,148-169` generates a 24-byte random recipient ID, independent 32-byte upload token (only SHA-256 verifier stored), 30-minute deadline, server-generated `staging/<id>/<random>` and `shares/<id>/archive.board.zip` keys, plus `shares/<id>/status.json`. Status is pending/ready/disabled/expired. `trial/share-usage-v1.json` and `trial/resolve-usage-v1.json` are R2 ETag compare-and-swap ledgers. The `trial-creator-v1` marker is legacy schema compatibility, not an active account.
4. `api/_lib/shareR2.ts:76-115` signs create-only PUT (`Content-Type: application/zip`, `If-None-Match: *`, 15 minutes), copies to a create-only final object with source ETag, and signs GET for at most 120 seconds. The installed SDK's request tests cover signed headers; [Cloudflare presigned URL documentation](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) confirms method/key/header scope and URL reuse. [Cloudflare conditional-operation documentation](https://developers.cloudflare.com/r2/api/s3/conditional-operations/) confirms its destination-only header and states source/destination copy conditions are not atomic. Private bucket and bucket-scoped token are required settings, not source-code guarantees.
5. `api/_lib/shareService.ts:172-268` checks the pending token, reserves one of five completion attempts, HEADs and reads at most 32 MiB, checks actual length/ETag/SHA-256, runs ZIP preflight, copies to the final key, and conditionally publishes ready. A retry returns the original ready timestamp/expiry. CAS conflict can leave an orphan final object; retry or cleanup can recover. The final key is isolated from outstanding browser PUTs. A missing final object makes a ready share temporarily unavailable. There is no transaction across R2 objects.
6. `src/BoardShareReceiver.tsx` handles direct `/share/<id>` navigation. `src/boardSharing.ts:79-137` first checks the local mapping, otherwise resolves and downloads a bounded archive, verifies digest, then imports. `src/storage.ts:361-424` atomically saves new board/assets/notes/share mapping in IndexedDB, remapping resource identities; a stale mapping is removed and remote reimport is attempted. Web Locks coordinate simultaneous tabs, with unique mapping as a fallback. Local copies and edits remain after remote expiration. Mobile currently shows the generic desktop-only screen (`src/main.tsx:41-54`).
7. `api/_lib/shareService.ts:288-341` exposes a bounded cleanup sweep (100 staging and 100 share keys per call), expires status before deletion, removes stale staging/orphan final objects, and retains metadata for 30 days. `scripts/cleanup-board-shares.mjs` invokes it manually with the operations key. `vercel.json` contains only a rewrite, no cron. An outstanding PUT URL can recreate staging after deletion until its signature expires; a later sweep or a verified staging lifecycle rule must remove it. R2 lifecycle deletion is asynchronous and cannot enforce precise link expiry.

Server preflight (`api/_lib/shareArchive.ts:3-150`) limits compressed input to 32 MiB, expanded bytes to 50 MiB, manifest to 1 MiB, each note to 1 MiB, all notes to 10 MiB, each image to 25 MiB, and 500 notes/200 images. It restricts paths, duplicate entries, manifest references and formats 2/3; limits are applied as decompressed chunks arrive. The browser importer (`src/boardArchive.ts:535-590`) has the larger manual-archive limits (up to about 261 MiB expanded), so validators are not identical. SHA-256 only establishes equality to the creator-declared bytes; ZIP and content checks are separate. The server holds decompressed files and chunks in memory and the client holds downloaded ZIP plus extracted files; peak memory can substantially exceed the compressed cap. Exact function memory settings are external/unverified. Markdown uses Milkdown/ProseMirror, images are imported as blobs, and note links require modifier-click (`src/panels/NotesEditor.tsx:423-450`). No automatic execution of shared code was found in this path, but adversarial Markdown/SVG/embed testing is incomplete.

## C. Findings, ordered by impact

### Confirmed defects

**F1 — High, release blocking: recipient link IDs enter analytics pageviews.** Trigger: opening `/share/<48-hex-id>`; consequence: a bearer-style recipient secret is exposed to the configured analytics services, extending access to anyone with those logs. Evidence: **code, high confidence**. `src/main.tsx:22-30,47-52,72-78` enables PostHog pageviews and renders Vercel Analytics without URL filtering. [PostHog's SDK reference](https://posthog.com/docs/libraries/js/reference) documents `$current_url` on pageview; [Vercel Analytics privacy documentation](https://vercel.com/docs/analytics/privacy-policy) says pageviews are automatic and `beforeSend` can modify their URLs. Autocapture and session recording being disabled do not disable pageviews. Analytics event payloads/account access were not inspected, so historical collection and retention are unverified. Minimal fix: redact `/share/<id>` to `/share/:id` in both providers before sending, including initial/session-entry URL properties; check server access/error logs and referrer policy separately. Acceptance: a clean recipient navigation emits no share ID in analytics requests/events or browser referrers, while normal page metrics remain.

**F2 — High, release blocking: a signed upload does not enforce the 32 MiB byte limit at R2.** Trigger: a malicious client obtains one ordinary create response and uses its 15-minute URL for an oversized single PUT. Consequence: R2 can accept/store and charge for an object before completion rejects its size; declared-byte reservations do not bound actual staging bytes. Evidence: **code + official platform documentation, high confidence**; no destructive live test. `api/_lib/shareR2.ts:97-107` signs method/key/type/create-only but not exact Content-Length; `api/_lib/shareService.ts:148-169,211-216` enforces declared 32 MiB at create and actual size only at completion. [Cloudflare's upload limits](https://developers.cloudflare.com/r2/objects/upload-objects/) permit a single PUT up to 5 GiB. The code issues at most 100 URLs/day, so the extreme theoretical accepted staging volume is 500 GiB/day (100 × 5 GiB), versus the 512 MiB *declared* daily reservation; actual throughput, account limits and deletion timing may lower this. The URL cannot overwrite the final archive, and create-only prevents replay while staging exists; after deletion the same URL can recreate staging until expiry. Minimal fix: put a real pre-ingest byte cap in the upload path (or a provider mechanism verified to enforce it), and limit abandoned staging retention; do not rely on completion to cap storage. Acceptance: a controlled test above 32 MiB is rejected before the object is stored, while a valid 32 MiB-or-smaller PUT completes; verify conditional PUT/replay against test R2 without quota exhaustion.

**F3 — High, release blocking: cleanup has no configured production invocation or failure alert.** Trigger: normal expiration, failed completion, orphan copy, or recreated staging; consequence: remote retrieval is blocked at expiry, but physical objects and metadata can accumulate, including oversized rejected uploads. Evidence: **code, high confidence** for absence in repository; **external** scheduling cannot be ruled out. `vercel.json:1-8` has no cron; `scripts/cleanup-board-shares.mjs:1-22` is manual; `api/_lib/shareService.ts:288-341` provides bounded work and retryable deletion but no automatic caller/alert. Existing sharing documentation says to run it manually; that is not evidence of a scheduled production job. Minimal fix: configure a protected production scheduler or operator job that drains cursors, repeats after transient failure, and alerts on failures/backlog; verify a staging lifecycle rule as secondary safety. Acceptance: a controlled expired fixture is made unavailable at deadline, its objects are later removed by an observed scheduled run, a failed delete is retried, and job failures are visible.

**F4 — Medium, release blocking until bounded: request body is allocated before the stated 2 KiB limit.** Trigger: `POST create/complete/cleanup` with chunked or misleading length; consequence: `request.text()` may allocate an arbitrarily large body up to platform limits before rejecting it, consuming function memory. Evidence: **code, high confidence**; no live oversized request. `api/boardShares.ts:13-21` checks the header, then reads the full body and checks character length. Extra JSON fields and unexpected Content-Type are also accepted (`api/boardShares.ts:68-92`), though typed fields are subsequently validated by the service. Minimal fix: stream-read with a byte cap before JSON parsing, reject unsupported Content-Type and exact-schema violations. Acceptance: a locally streamed body just over 2 KiB is rejected after at most 2 KiB plus one chunk, with no full-body allocation.

**F5 — Medium, release blocking for atomic-import claim: theme installation can outlive failed board import.** Trigger: a valid archive embeds a custom theme but IndexedDB board/asset/mapping commit fails (quota, duplicate mapping, tab race); consequence: a theme remains in the recipient's library despite no board import. Evidence: **code, high confidence**; failure injection not yet run. `src/boardArchive.ts:450-487` calls `importStoredTheme` before `importBoardContent`; `src/storage.ts:386-389,519` use separate transactions. The board/assets/notes/mapping transaction itself is atomic. Minimal fix: include theme and board writes in one transaction, or compensate a newly installed theme after a failed board transaction without removing any pre-existing theme. Acceptance: inject a board-write failure after theme preparation; no new theme, board, asset or mapping remains.

### Unverified external prerequisites and residual risks

**P1 — High, release blocking: production settings and deployed artifact are not verified.** Trigger: promotion without a private isolated production bucket, scoped credentials, correct origin/CORS, anonymous deployment access, or known commit; consequence: failed shares, cross-environment data exposure, or inaccessible links. Evidence: **external setting not verified**, high confidence in the *gap*, no claim settings are wrong. Relevant checks: `api/_lib/shareConfig.ts:12-49`, `api/_lib/shareR2.ts:14-31`, `api/boardShares.ts:68-96`, deployment fingerprint above. Minimal fix: complete the configuration matrix and inspect actual Vercel/R2 settings and deployment SHA. Acceptance: a fresh production-origin smoke test with isolated test board and verified deployment SHA; no Preview credential can access production bucket.

**P2 — Medium: R2 concurrency and interruption behavior needs a safe integration check.** Trigger: two completion requests, cleanup racing completion, copy succeeds/status CAS fails, status ready/final absent, or PUT replay after staging deletion; consequence: 409/503 to creator or recipient, orphan bytes or unavailable share. Evidence: **code + unit**, medium confidence in general recoverability; **real R2 race not verified**. `api/_lib/shareService.ts:172-250,288-341` handles many CAS conflicts and retries; `api/_lib/shareR2.ts:76-115` uses SDK middleware for Cloudflare's conditional copy. Source and destination conditions are explicitly non-atomic in [R2 documentation](https://developers.cloudflare.com/r2/api/s3/conditional-operations/). A cleanup scan can see an old pending status and delete a final object while completion is publishing; resolve then reports temporary unavailability until an operator repairs/retries. Minimal fix: coordinate cleanup and publication with status checks after copy, verify final presence before/after ready publication, and provide an orphan/ready-missing repair path. Acceptance: controlled R2 fixtures and concurrent calls converge on one ready share or an expired state, with no permanently ready-but-missing archive and eventual orphan removal.

**P3 — Medium: real content and browser coverage is incomplete.** The current Preview diagnostic independently reproduced one small anonymous create (`201`), complete (`200`), resolve (`200`), separate clean-recipient import, refresh/reopen, and no download event. It did not capture console errors or exercise recipient edits, a device image or curated R2 image. Existing **local browser** manual-archive baseline covers notes/formatting, device image, theme, panel layout/order, camera, independent edits and reload; prior user-reported live tests additionally covered a local image and edits, but were not independently repeated here. A real curated R2 image, bundled collections, Safari/iOS/Firefox, mobile error clarity, and matched-viewport pixel fidelity remain unverified. The feed root/CORS is a prerequisite for curated-image export (`src/boardArchive.ts:218`, `src/curatedImageCollections.ts:61`). Minimal check: one small real curated-image share and clean-recipient edit/reopen at matched desktop viewports, plus deliberate browser coverage claims. Mobile is presently unsupported; it should say so clearly when a share link is opened.

**P4 — Medium: sharing-related dependency advisories require reachability triage.** `npm audit --omit=dev` found 31 advisories (1 low, 28 moderate, 2 high, 0 critical); installed sharing transport packages `@aws-sdk/client-s3`, presigner and `fflate` did not appear in the advisory output. `prosemirror-view@1.42.2` has a high paste-XSS advisory fixed in 1.42.3, and `markdown-it@14.3.0` has denial-of-service advisories; both arrive through editor/tldraw dependencies. The paste finding requires user paste and is not established as an automatic shared-board-open exploit; `markdown-it` reachability from shared notes is likewise unproven (notes use Milkdown). Evidence: **local audit + dependency tree**, medium confidence. Minimal fix: update compatible affected editor dependencies and test adversarial shared notes/paste without assuming every advisory is exploitable here. Acceptance: audit and targeted editor tests show the vulnerable path is fixed or demonstrably unreachable.

### Accepted product limitations and optional improvements

IP-based limits affect shared networks and can be bypassed by IP rotation; they are friction, not identity. A user who hits a limit receives a retry time or general 15/30-minute guidance (`api/_lib/shareService.ts:85-145`). Resetting browser storage does not reset the IP budget. There is no creator dashboard, mandatory login, early-deletion UI, or extension; those are within the stated product requirements. Legacy ready trial records lacking `expiresAt` remain indefinitely resolvable (`api/_lib/shareService.ts:52-68,253-268`); document and execute a separate migration/retirement policy before claiming **all** links expire. Old pending records cannot complete without the new token. Optional improvements: share-specific mobile notice, clearer retry classification, exact-schema request validation, and migration of old owner-marker names.

### Limits, abuse, and illustrative cost

Enforced reservations: 4 creates/source/15 min, 12/source/rolling day, 100/global/rolling day, 4 pending/source and 20 pending/global until a 30-minute deadline, 512 MiB *declared* active bytes/day, 32 MiB declared archive, 5 valid-token completion attempts/pending share, 60 resolves/source and 1,000/global per 15 min (`api/_lib/shareService.ts:85-169`). CAS on R2 ledger serializes reservations; conflict retries are bounded. Failed creates can retain count reservations until the rolling window; pending bytes/slots release after deadline. Resolve limits do not cap reuse of a signed GET URL, previously imported local opens, browser PUT bytes, or validation work across 100 legitimate-looking creates. Source IP rotation bypasses per-source thresholds; global counts remain.

Illustrative **estimates**, not enforced spend caps: 100 successful 5 MiB shares/day yield 500 MiB of final objects/day and roughly 30,000 Class A operations/month for creates/copies/status writes before cleanup and retries; 1,000 resolves/15 min can approach 96,000/day if sustained, each doing ledger CAS, status read and final HEAD, with further GETs from reusable links. One malicious 5 GiB PUT per issued URL could briefly stage up to 500 GiB/day if all 100 URLs were used, independent of 512 MiB declared reservations. At [current R2 Standard pricing](https://developers.cloudflare.com/r2/pricing/) ($0.015/GB-month storage, $4.50/million Class A, $0.36/million Class B, free egress, free-tier/rounding rules apply), 500 GiB retained for a full month is about $7.50 storage; actual daily peaks, operations, Vercel function duration, retries and billing granularity can change costs. The global ledger caps create count and declared bytes, not all requests or downloads. No load/quota test was run.

## E. Exact production setup checklist

The six server-side variables are read by `api/_lib/shareConfig.ts:12-49`; values must have no `VITE_` prefix. Preview and Production should use isolated buckets and credentials. Whether current external settings meet these requirements was not verified.

| Variable | Type | Production value/source | Preview vs Production |
| --- | --- | --- | --- |
| `BOARD_SHARE_R2_ENDPOINT` | Config | HTTPS S3 endpoint for the intended Cloudflare account | May share account endpoint only if buckets/tokens isolated; verify |
| `BOARD_SHARE_R2_BUCKET` | Config | Dedicated **private** production R2 bucket | Must differ |
| `BOARD_SHARE_R2_ACCESS_KEY_ID` | Secret | Bucket-scoped Object Read & Write API token ID | Must differ |
| `BOARD_SHARE_R2_SECRET_ACCESS_KEY` | Secret | Matching scoped token secret | Must differ |
| `BOARD_SHARE_ALLOWED_ORIGIN` | Config | Canonical production HTTPS origin after redirects, e.g. `https://my-states.xyz` if that is the actual canonical origin | Must differ; exact Origin and generated links depend on it |
| `BOARD_SHARE_SESSION_SIGNING_KEY` | Secret | 32 random bytes as 64 lowercase hex; operations bearer and IP HMAC key | Must differ; rotate with operational plan |
| `BOARD_SHARE_CREATOR_PASSWORD_HASH` | Obsolete | Remove; current API does not read it | Obsolete in both |

Also verify: production R2 browser CORS exact canonical origin, `GET`/`PUT`, allowed headers `Content-Type` and `If-None-Match`; private bucket, token bucket scope, no public R2 domain; no leaked server values in `VITE_` bundles; production deployment accessible anonymously; production canonical redirect and direct `/share/<id>` rewrite; curated image-feed CORS and `VITE_IMAGE_COLLECTIONS_BASE_URL` if that feature is offered; analytics URL redaction; actual scheduled protected cleanup plus failure alert; staging-only R2 lifecycle rule as fallback; Vercel plan support for selected cron/edge control. `VITE_POSTHOG_HOST`, `VITE_POSTHOG_PROJECT_TOKEN`, `VITE_POSTHOG_INTERNAL_TESTER`, `VITE_LOCAL_ORIGIN`, and `VITE_TLDRAW_LICENSE_KEY` are general app/client configuration rather than share-server secrets; check their production routing and analytics privacy separately. No additional edge service is required by current code, but a narrow emergency edge rule is useful.

The application returns 503 when required sharing config is missing/invalid or R2 is unavailable; unrelated board editing can continue. No create-only kill switch exists. For an incident, a scoped edge/WAF rule blocking `POST /api/boardShares?action=create` can stop new uploads while keeping resolve available, **if supported and tested on the production plan**; a code-level create-only flag is the durable fix. Removing a required env value would also break existing link resolution and is unsuitable for a normal incident stop. Operational cleanup/disable must retain a protected credential. Current API catches unexpected failures without logging sensitive data, but also provides little failure visibility; add structured counts and error classes for create/upload/complete/resolve/import/cleanup without board content, tokens, signed URLs or share IDs. Server access logs and analytics routing require separate verification.

### Final summary

**Verdict:** not ready. **Confirmed blockers:** analytics path disclosure, unconstrained presigned PUT bytes, absent scheduled cleanup, unbounded API body read, and non-atomic theme import. **Unresolved:** production isolation/CORS/scheduler/deployed SHA, real R2 race and curated-image checks, other browsers. **Single next action:** implement and verify the five blockers on this branch, starting with analytics URL redaction and a true pre-ingest upload limit, then repeat this review before release.
