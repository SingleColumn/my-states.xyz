## 3. Browser requests and CORS

All API requests are same-origin to `/api/boardShares`; API JSON bodies are capped at 2,048 UTF-8 bytes, require `application/json` (optionally `; charset=utf-8`), and enforce exact fields. `src/boardSharing.ts` sets `credentials: 'same-origin'` and `cache: 'no-store'` for these API requests. There is no creator login/cookie requirement. The Origin check on create/complete is a browser-origin boundary, not authentication.

| Flow | Destination and route | Method / request content type | Browser-sent headers and authorization | Credentials / preflight / response data |
|---|---|---|---|---|

### Required CORS policies

**Upload Worker:** current source implements this response for OPTIONS: exact `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods: PUT`, `Access-Control-Allow-Headers: Authorization, Content-Type`, `Access-Control-Max-Age: 600`, `Vary: Origin`. It also returns the exact allow-origin on upload responses. The Worker configuration's `BOARD_SHARE_ALLOWED_ORIGIN` controls it. No wildcard origin and no credentials allowance.

**Private sharing R2 bucket:** only signed GET of final archives is browser-originated. In Cloudflare R2 CORS JSON format, replace the placeholder with the exact canonical app origin for that environment:

```json
[
  {
    "AllowedOrigins": ["<EXACT_APP_ORIGIN>"],
    "AllowedMethods": ["GET"],
    "MaxAgeSeconds": 600
  }
]
```

No `PUT`, `HEAD`, `DELETE`, `If-None-Match`, `Authorization`, or `ETag` exposure is needed for browser-to-R2 traffic. The browser needs only response `Content-Length`, which is a CORS-safelisted response header. Keep the bucket private and without a public R2 domain. Cloudflare documents R2 CORS rules and response-header behavior at [Configure CORS](https://developers.cloudflare.com/r2/buckets/cors/).

**Public curated image source:** only if the production build uses a remote `VITE_IMAGE_COLLECTIONS_BASE_URL`. Its host must return browser CORS allowing the exact app origin and `GET` for index/manifests/images. Example in the source provider's own CORS format: origin `<EXACT_APP_ORIGIN>`, method `GET`, no custom request headers. This is a different source from the private share bucket unless explicitly configured to be the same public service.

`workers.dev` is sufficient; no Worker custom domain is required. Actual Worker URL must be taken from the deployed Worker output/dashboard, then entered as `BOARD_SHARE_UPLOAD_ORIGIN`. Do not infer it from `name` alone because the account's `workers.dev` subdomain is external configuration.

IDs in key templates below are placeholders; the generated share ID is 48 lowercase hex characters. No actual IDs are shown.

Prefixes overlap by design: `shares/` contains both `status.json` and `archive.board.zip`, and `trial/` contains two different usage ledgers and cleanup state. Do not put a lifecycle expiration on either parent prefix. The only safe candidate is a rule restricted to `staging/`.

**Legacy and failures:** ready metadata lacking `expiresAt` remains accessible indefinitely until disabled/operator action; it is not covered by new 24-hour expiration logic. Abandoned pending uploads become expired after 30 minutes once cleanup scans them; their archive keys are removed and expired metadata retained 30 days. If a Worker upload is in flight while cleanup expires/deletes a share, it rechecks pending status and deletes its own late object; a later sweep handles late recreation/races. A status-less staging object and a status-less final archive are treated as orphans and deleted by cleanup. Partial cleanup can remove objects before a later operation fails; the page cursor is not committed on failure, so the page is retried and deletes are idempotent. A final archive that conflicts with a publication/cleanup race is guarded by conditional status updates and can be repaired from retained staging. These R2 race claims are code plus mock tests, not verified real-R2 guarantees.

**Lifecycle rule:** in Cloudflare R2 bucket Settings → Object Lifecycle Rules, add an enabled rule with prefix exactly `staging/`, action “Delete objects”, age “2 days” (48 hours). Do not use `shares/`, `trial/`, empty prefix, or a rule on the whole bucket. R2 lifecycle deletion is eventual (Cloudflare says objects are typically removed within 24 hours of the expiry value), so the app's timestamp checks remain the logical access control. See [Object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/).

## 5. Cleanup configuration

**Handler:** `POST /api/boardShareCleanup` (Vercel path schedule) wraps `POST /api/boardShares?action=cleanup`. The API accepts either an empty scheduler POST or a JSON body for operator-supplied optional `stagingCursor` and `sharesCursor`. Both cursors must be strings if supplied. A successful scheduled call returns JSON with `removed`, `backlog`, and `lastSuccessAt`. It requires `Authorization: Bearer <64-lowercase-hex key>` matching `BOARD_SHARE_SESSION_SIGNING_KEY`. There is no browser CORS flow for this endpoint.

**Schedule declared in source:** `vercel.json` declares schedule name `board-share-cleanup`, UTC cron `0 * * * *` (hourly), path `/api/boardShareCleanup`, method POST. Vercel's current docs support POST path schedules, Preview branches and Production on all plans (Schedules are in beta), and require `CRON_SECRET` for a public path target. Static schedule configuration takes effect when deployed; a project can still disable it. Therefore:

| State | Finding |
|---|---|
| Implemented handler | Yes, source present at `api/boardShareCleanup.ts`; delegates into the protected shared handler. |
| Schedule declared | Yes, current `vercel.json`. |
| Schedule deployed/active | **External unverified.** Requires a deployment containing this config and schedule enabled for the relevant environment/branch. |
| Successful scheduled execution observed | **No.** No Vercel account access or current schedule history was available. |

To set it up, enter `CRON_SECRET` in each Vercel environment equal to the same environment's `BOARD_SHARE_SESSION_SIGNING_KEY`, deploy that environment, verify the schedule exists/enabled in Vercel Schedules, then use the dashboard's Run now/Execution history or await a scheduled run. Vercel sends the bearer automatically for a path schedule; no adapter is required. The existing `api/boardShareCleanup.ts` is the adapter from Vercel's path to the authenticated cleanup action. Vercel path schedules do not provide automatic retries; the next hourly run retries because R2 cursor state advances only after a successful page. Vercel docs: [Schedules](https://vercel.com/docs/schedules), [Handling scheduled runs](https://vercel.com/docs/schedules/handle-runs).

One invocation lists at most 100 keys under `staging/` and 100 keys under `shares/` (the latter prefix intermixes status and archive keys). It may inspect statuses from that page and delete keys among those pages; it does not recursively drain the entire bucket in one scheduled invocation. `trial/cleanup-state-v1.json` stores both continuation cursors and last successful timestamp. Each later invocation resumes from those cursors; when a listing ends, its cursor clears and the next pass starts again at the beginning. Retained legacy/active records are scanned and skipped. A failed list/read/delete/update does not commit next cursor; next run repeats work. Concurrent invocations do not take an exclusive lease: ETag compare-and-swap protects cursor-state advancement, status ETags guard transitions, and duplicate deletions/pages can occur. Real R2 continuation behavior during deletion remains unverified.

**Failure visibility:** cleanup endpoint sends the generic webhook only when its response is 5xx, and only if `BOARD_SHARE_CLEANUP_ALERT_URL` is configured. Webhook delivery has a 3-second timeout and no retry. A 401 caused by a missing/wrong `CRON_SECRET` is not alerted by that webhook; the Vercel schedule run history should show it. Missing runs also do not trigger the webhook. Monitor schedule history and compare `lastSuccessAt` / `backlog` independently. The cursor is in R2, but there is no read-only public status endpoint. Vercel run history may show HTTP result; actual account visibility/configuration is unverified.

**Retention:**

| Data | Logical cutoff | Physical cleanup/retention |
|---|---|---|
| New share link | `expiresAt = publishedAt + 24h`; API resolve refuses at/after that instant. Signed GET is at most 120 seconds and shortened to finish before the expiry margin. | Final and staging archives are removed by a later cleanup sweep; hourly schedule means normally delayed beyond the instant. R2 delete/lifecycle is asynchronous. |
| Pending failed/abandoned upload | Upload deadline is 30 minutes from create; Worker refuses once status/deadline is no longer pending. | Cleanup marks expired, deletes staging/final objects, retains status 30 days from its updated timestamp, then removes status. A late in-flight Worker write is rechecked and may need a subsequent sweep. |
| Disabled share | Immediately unavailable after status changes to disabled. | Cleanup removes stage/final; status retained 30 days from disable `updatedAt`. The direct disable handler deletes archives immediately after metadata update, with cleanup as retry. |
| Legacy ready without `expiresAt` | No automatic expiry; resolve allows it and signs up to 120 seconds. | No automatic cleanup of that ready record/archive. Explicitly inventory/retire before Production data migration; do not silently import test objects. |
| Usage ledger rows | Create/source rows age out of calculations after 24h; resolve rows after 15m. | Arrays are pruned on the next relevant request; ledger objects themselves have no TTL. |
| Cleanup state | N/A | Persists; do not lifecycle-delete. |

## 6. Rate limits and external dependencies

| Limit | Actual value | Enforcement / caveat |
|---|---:|---|
| Creates per source | 4 per rolling 15 minutes; 12 per rolling 24 hours | R2-backed `trial/share-usage-v1.json`, ETag compare-and-swap, in `shareService.ts`. Source is HMAC of client IP. |
| Global create count | 100 per rolling 24 hours | Same ledger. |
| Pending uploads | 4 per source and 20 global until 30-minute deadline | Counts unfinished ledger reservations; proxy for in-flight work, not a live socket/concurrency semaphore. |
| Global declared archive capacity | 512 MiB of active/completed declared bytes per rolling day | Reservation accounting based on client-declared size, capped separately at 32 MiB. It is not a bucket storage quota or billing cap. |
| Upload actual bytes | 1–32 MiB per share; Worker checks actual stream byte count equals status's declared length and only commits through `FixedLengthStream` after EOF. | This is the actual storage-size guard for new uploads. Worker tests are mocks; real Worker/R2 behavior not verified. Excess bytes are not committed to R2 by the intended code path. |
| Archive validation | 32 MiB compressed; 50 MiB expanded; 1 MiB manifest; 1 MiB per note; 10 MiB total notes; 25 MiB per image; 500 notes; 200 images | `api/_lib/shareArchive.ts`, server-side ZIP preflight. This limits accepted content, not all CPU/memory spent on malicious requests; Vercel function handling and memory still matter. |
| Completion/validation attempts | At most 5 pending-share attempts with a valid upload token | Attempt is reserved before expensive HEAD/read/ZIP validation. Ready retries are idempotent and return before this counter; request volume itself is not capped by this counter. |
| Resolve | 60 per source per 15 minutes; 1,000 global per 15 minutes | R2-backed rolling resolve ledger. Does not cap reuse of a signed GET URL during its 120-second life or already imported local copies. |
| Upload-token replay | One successful conditional stage write per key; pending status/token/deadline rechecked before and after write | Worker checks SHA-256 verifier, pending state, deadline, `head` and create-only `If-None-Match: *`. Completed/expired status fails Worker authorization. |
| API request body | 2,048 UTF-8 bytes; exact JSON shape | `api/boardShares.ts` counts stream bytes, checks Content-Type and rejects extra/missing fields. Platform may reject oversized ingress before handler; normal API bodies are tiny. |
| Worker request ingress | Platform-dependent ceiling | Cloudflare documents body limits by zone/domain plan (Free/Pro 100 MB, Business 200 MB, Enterprise configurable); Worker app limit remains 32 MiB. A client can still consume Worker ingress/invocation capacity with a rejected request. Verify which limit applies to the deployed `workers.dev` endpoint. |

**Trusted client address:** when `VERCEL === '1'`, code trusts the first `X-Forwarded-For` element only if it parses as an IP. The code comment relies on Vercel overwriting this at ingress. Confirm current Vercel behavior and do not put an untrusted proxy in front without revisiting source identity. Other environments fail closed (503), rather than trusting arbitrary client headers. IP rotation/shared NAT can defeat or over-constrain per-source thresholds; global caps still apply.

**External rate-limit setup:** no third-party rate-limiting service, WAF rule, or external rate-limit configuration is required for the code's stated create/resolve limits. R2 compare-and-swap ledgers implement those application limits. Cloudflare/Vercel platform request, duration, concurrency and billing limits remain external capacity boundaries, not per-share spending ceilings. Cloudflare Workers Free currently documents 100,000 requests/day; check the account plan and Worker spending controls. The R2 storage/account budget is not hard-capped by the 512 MiB declared-byte ledger: it does not cap repeated resolve downloads, rejected Worker ingress, or all platform operations. No actual external rule is independently verified.

Vercel currently documents a 4.5 MB default Function request/response payload ceiling and a 20 MiB opt-in beta requiring 4 GB performance memory; neither is needed for sharing because API JSON is at most 2 KiB and archives bypass Vercel through the Worker. Do not enable a large-body option for sharing. Confirm function runtime/config and keep the streaming JSON check. See [Vercel Function limits](https://vercel.com/docs/functions/limitations). Cloudflare documents Worker request body limits, request quotas and 128 MB memory at [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

**Emergency stop:** there is no code-level create-only kill switch. Removing a required R2 or origin variable breaks resolve as well, so it is not a safe emergency stop. An edge/WAF rule that blocks only `POST /api/boardShares?action=create` could stop new share creation while allowing resolve and cleanup, but no such rule is configured/verified and query matching must be confirmed on the chosen plan. A durable code/config-only create switch would require a Codex change. Existing recipient resolution and cleanup should remain available while stopped.
